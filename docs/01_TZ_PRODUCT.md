# 01. Подробное техническое задание: продукт и функции

## 1. Паспорт проекта

**Наименование:** «Идеи для региона».
**Контекст:** Smart City, область Абай, хакатон.
**Тип решения:** адаптивная веб-платформа для сбора, структурирования и рассмотрения IT-идей жителей.
**Заказчик MVP:** постановка задачи организаторов; реальные государственные интеграции не подтверждены.
**Цель:** продемонстрировать полный цикл от идеи жителя до понятного ответа сотрудника.

Исходное описание проблемы — часть задания хакатона, а не результат отдельного социологического исследования. Продуктовая гипотеза: структурированная подача и видимая история уменьшают потери контекста при рассмотрении предложений. Проверка гипотезы требует пилота после хакатона.

## 2. Задача и ценность

Житель должен иметь возможность предложить цифровое улучшение без знания структуры органов и специальной терминологии. Сотрудник должен получить не набор разрозненных сообщений, а карточку с проблемой, решением, территорией, категорией, материалами и историей взаимодействия.

MVP должен отвечать на пять вопросов: **что предлагается; какую проблему решает; где актуально; кто сейчас рассматривает; какой следующий шаг**.

Особенности предлагаемого решения:

1. **Объяснимый маршрут.** В карточке видны категория, дополнительные темы и понятное объяснение распределения. Сотрудник может исправить маршрут с указанием причины.
2. **Паспорт идеи.** Проблема, цифровое решение, место, ожидаемая польза и следующий шаг представлены одинаково в обоих кабинетах.
3. **Прослеживаемость.** Статусы, запросы уточнений, ответ и перенаправления фиксируются событиями, а не перезаписывают историю.
4. **Устойчивость без AI.** Базовая маршрутизация работает локально по правилам. LLM — дополнительный консультант, не обязательная точка отказа.

Это проектные отличия, а не заявление, что аналогичных функций не существует в других системах.

## 3. Объём и ограничения

### 3.1. Обязательный P0

- Регистрация и вход жителя; вход сотрудника; серверная проверка ролей.
- Создание и редактирование черновика идеи, прикрепление материала, отправка.
- Хранение пользователей, идей, статусов, комментариев и маршрутов в PostgreSQL.
- Автоматическое распределение по категории/правилам с объяснением.
- Кабинет жителя: идеи, детали, история, ответы и уведомления.
- Кабинет сотрудника: очередь, поиск, фильтры, ответственный, статусы, уточнения.
- Минимальная служебная функция администратора: очередь разбора и смена маршрута.
- Мобильный интерфейс и развёртывание по инструкции.
- Синтетические демоданные и воспроизводимый финальный сценарий.

### 3.2. Дополнительный P1

AI-улучшение текста с подтверждением автора; проверка классификации вторым AI-этапом; похожие идеи; паспорт небольшого пилотного проекта; агрегированная аналитика; казахская локализация всех интерфейсов; модерируемая публичная витрина.

### 3.3. Вне MVP

Официальная регистрация обращения; интеграции с eOtinish/eGov/ЭЦП; платежи; закупки; обещание финансирования; мобильные приложения; фактическое управление светофорами или датчиками; автоматическая реализация предложений; автоматическое отклонение по выводу LLM; оценка жителей по социальному профилю.

## 4. Роли и доступы

| Действие | Гость | Житель | Сотрудник | Администратор |
|---|---|---|---|---|
| Читать описание сервиса | Да | Да | Да | Да |
| Создавать идеи | После входа | Да | Через отдельный аккаунт жителя | Через отдельный аккаунт жителя |
| Читать частную идею | Нет | Только свою | Только текущей организации | Все, с аудитом действий |
| Изменять черновик | Нет | Только свой | Нет | Нет |
| Назначать ответственного | Нет | Нет | В своей организации | В текущей организации идеи |
| Менять статус | Нет | Ответить на уточнение | В своей организации | Да, по тем же бизнес-правилам |
| Менять организацию | Нет | Нет | Запросить служебным комментарием | Да, с причиной |
| Читать внутренние заметки | Нет | Нет | В своей организации | Да |
| Смотреть контакты автора | Нет | Собственные | Только доступная идея | Да, по служебной необходимости |

Администратор — не обход бизнес-правил: например, отклонение без причины недопустимо и для него. Проверка роли в браузере служит только отображению элементов; окончательный доступ проверяет сервер.

## 5. FR-01 — регистрация, вход, сессия

Житель вводит имя, email и пароль, принимает текст согласия на обработку данных в рамках демонстрационного сервиса. Email уникален после нормализации. Имена не требуют паспортного формата. Пароль: 12–128 символов, разрешены пробелы и Unicode. В MVP email не подтверждён; интерфейс не выдаёт пользователя за идентифицированного государством.

Сотрудники и администратор создаются через seed/служебный CLI, не через публичную форму. Пользователь не может передать себе роль в JSON. Сессия хранится серверно; выход отзывает её. На публичном стенде демонстрационный доступ должен быть ограничен отдельно.

**Приёмка:** после входа житель попадает в «Мои идеи», сотрудник — в очередь. Запрос к чужой карточке не раскрывает существование объекта. После выхода прежняя cookie не даёт доступа.

## 6. FR-02 — форма и черновик

Форма состоит из трёх шагов: **идея → место и материалы → проверка и отправка**. На компьютере справа отображается краткий паспорт, на телефоне — итоговый экран.

| Поле | Правило |
|---|---|
| Название | 10–120 символов после trim; обязательное |
| Описание проблемы | 30–3 000 символов; обязательное |
| Предлагаемое решение | 30–3 000 символов; обязательное |
| Категория | `AUTO` или значение справочника; `AUTO` — выбор по умолчанию |
| Населённый пункт/территория | Идентификатор активного справочника; обязательное |
| Место подробнее | До 300 символов; необязательное; без требования домашнего адреса |
| Ожидаемая польза | До 1 000 символов; необязательное |
| Материалы | До 3 файлов; JPG/PNG/WebP/PDF; до 5 MiB каждый |
| Согласие | Обязательный boolean + серверная версия текста согласия |

Черновик допускает неполные поля. Полная валидация выполняется при отправке. Сохранение черновика — в БД; индикатор «Сохранено» появляется после успешного ответа сервера. Автосохранение с debounce допустимо, но кнопка сохранения и корректный повтор обязательны. Вложения загружаются только после создания серверного черновика.

Не сохранять тексты и контакты в `localStorage` по умолчанию. При ошибке сети поля остаются в памяти открытой формы. При обновлении страницы восстанавливается последнее сохранённое состояние с честным указанием времени.

**Приёмка:** ошибка конкретного поля видна рядом с ним; введённое не исчезает; повторный клик по отправке не создаёт вторую идею.

## 7. FR-03 — регистрация идеи и номер

После отправки: сервер валидирует поля и вложения, рассчитывает маршрут, присваивает номер вида `ABAI-2026-000123`, создаёт событие «Получена» и уведомление. Всё фиксируется атомарно. Внутренний UUID не заменяет отображаемый номер; номер не даёт публичного доступа.

Номер создаётся через последовательность БД, а не `COUNT(*) + 1`. Пропуски номеров допустимы. Статус после отправки — `RECEIVED`, даже если маршрут требует ручной проверки. Не смешивать «анализ» с пользовательским статусом рассмотрения.

Текст успеха: «Идея зарегистрирована на платформе. Номер …». Дополнительно отображаются демонстрационная очередь и её объяснение.

## 8. FR-04 — категории и распределение

Категории: транспорт; ЖКХ; образование; экология; безопасность; здравоохранение; туризм и культура; доступная среда; другое. Эти названия — проектный справочник, не утверждение об официальной структуре органов.

Подробный алгоритм определён в [04_SMART_ROUTING_AI.md](04_SMART_ROUTING_AI.md). Для P0 используются текстовые признаки и выбор категории автором. Несколько тем допускаются, но у заявки только **одна текущая ответственная организация**, иначе возникает размытая ответственность.

При конфликте признаков, неизвестном маршруте или недостатке данных создаётся очередь ручного разбора. Заявка не исчезает и не отклоняется. Назначение конкретного сотрудника остаётся действием человека.

## 9. FR-05 — кабинет жителя

Экран «Мои идеи» показывает номер, название, категорию, дату, текущий статус, последнюю активность и признак запроса уточнений. Черновики выделены отдельно. Доступны поиск по своим идеям и фильтр по статусу.

Карточка содержит исходное предложение, материалы, объяснение маршрута, публичную историю, ответственного в формате отображаемого имени, запрос уточнений и опубликованные ответы. Контакты и внутренние заметки сотрудников не раскрываются.

После отправки исходный текст не редактируется задним числом. Уточнение добавляется отдельным сообщением. Автор не меняет статус произвольным значением.

## 10. FR-06 — кабинет сотрудника

Очередь содержит только идеи текущей организации сотрудника. Колонки: номер; название; категория; территория; статус; дата поступления; ответственный; признак ручной проверки. На мобильном — те же данные карточками.

Фильтры: текстовый поиск, категория, территория, статус, ответственный, «без ответственного», дата от/до. Сортировка по умолчанию — новые поступления сверху; пользовательская сортировка ограничена известными полями. Пагинация — 20 записей, максимум 100 на запрос. Выбор фильтров отражается в URL, без помещения контактов или содержимого частных идей в адрес.

В карточке: публичная часть, контакты автора, маршрут, история, заметки, назначение и изменение статуса. Основное действие при `RECEIVED` — «Взять на рассмотрение», а не случайный выпадающий список без объяснений.

## 11. FR-07 — назначение и перенаправление

Сотрудник может назначить активного коллегу из своей организации или себя. Назначение фиксируется в истории служебных действий; житель видит актуального ответственного без внутренних данных.

Администратор может исправить категорию и/или текущую организацию с причиной 10–1 000 символов. Новая организация берётся только из справочника, не из произвольного текста AI. При смене организации прежний ответственный сбрасывается. Все записи маршрутизации сохраняются; идея не клонируется и не меняет номер.

В P0 перенаправление разрешено для `RECEIVED`, `UNDER_REVIEW`, `NEEDS_INFO`, `IN_PROGRESS`; для терминальных статусов запрещено. Текущий статус сохраняется, версия карточки увеличивается. Старый сотрудник теряет доступ, если больше не входит в текущую организацию идеи.

## 12. FR-08 — статусы и допустимые переходы

Шесть пользовательских статусов из задания сохраняются без переименования смысла. `DRAFT` — техническое состояние до подачи, а не седьмой статус рассмотрения.

| Код | Текст | Смысл |
|---|---|---|
| `RECEIVED` | Получена | Платформа сохранила и зарегистрировала идею |
| `UNDER_REVIEW` | На рассмотрении | Сотрудник начал изучение |
| `NEEDS_INFO` | Нужны уточнения | Автору задан конкретный вопрос |
| `IN_PROGRESS` | В работе | Принято решение о следующих действиях по идее |
| `COMPLETED` | Завершена | Опубликован результат или итоговый ответ |
| `REJECTED` | Отклонена | Указана обоснованная причина невозможности дальнейшего продвижения |

Допустимые переходы:

```text
DRAFT -> RECEIVED
RECEIVED -> UNDER_REVIEW
UNDER_REVIEW -> NEEDS_INFO | IN_PROGRESS | REJECTED | COMPLETED
NEEDS_INFO -> UNDER_REVIEW          # после ответа автора либо действия сотрудника с причиной
IN_PROGRESS -> NEEDS_INFO | COMPLETED | REJECTED
COMPLETED / REJECTED -> нет переходов в P0
```

Для `NEEDS_INFO`, `REJECTED`, `COMPLETED` обязателен публичный комментарий 20–2 000 символов. Для `COMPLETED` дополнительно обязателен тип результата: `ANSWER_PROVIDED`, `PILOT_PLANNED`, `IMPLEMENTED` или `FORWARDED_EXTERNALLY`. Последний допускается только при действительном подтверждении передачи; в демонстрационном сценарии не использовать. «Завершена» с типом `ANSWER_PROVIDED` не означает, что инфраструктура уже построена.

Для входа в `UNDER_REVIEW`/`IN_PROGRESS` нужен активный ответственный. Кнопка «Взять на рассмотрение» может атомарно назначить текущего сотрудника и выполнить переход. Исключение: ответ автора после перенаправления допускает `UNDER_REVIEW` без ответственного; такая идея видна новой организации в фильтре «Без ответственного». Переход на тот же статус без нового события отклоняется как некорректный.

## 13. FR-09 — уточнения и комментарии

Комментарий имеет видимость `PUBLIC` или `INTERNAL`. Публичный комментарий доступен автору идеи и сотрудникам с доступом к ней. Внутренняя заметка — только текущей организации и администратору. В данном контексте `PUBLIC` означает видимый автору, **не автоматически доступный всему интернету**.

При запросе уточнений автор получает уведомление и форму ответа. Ответ 10–3 000 символов сохраняется отдельным комментарием, может включать допустимые материалы, переводит карточку в `UNDER_REVIEW` и уведомляет ответственного либо организацию, если ответственный отсутствует после перенаправления. Исходная идея остаётся неизменной.

Редактирование/удаление опубликованных ответов и заметок в P0 не реализуется; исправление — новым сообщением. Вложения к уточнению подчиняются тем же ограничениям; общий максимум для идеи в P0 — 3 активных файла, поэтому форма объясняет оставшийся лимит.

## 14. FR-10 — история и уведомления

История упорядочена по времени и дополнительному идентификатору события; одинаковые timestamps не должны ломать порядок. События: подача, статус, назначение, перенаправление, публичный ответ, запрос уточнений, ответ автора.

Уведомления внутри приложения: регистрация идеи, запрос уточнений, публичный ответ, новый статус, перенаправление. Колокольчик показывает число непрочитанных. Нажатие открывает доступную карточку и отмечает уведомление прочитанным. Обновление — при возвращении на вкладку и опросе раз в 10 секунд на активном экране. Нельзя показывать повторные уведомления от одного события.

Email/SMS/мессенджеры не обязательны. Формулировка «уведомление отправлено» не должна означать внешнее письмо, если создана только внутренняя запись.

## 15. FR-11 — поиск и аналитика

Поиск выполняется на сервере по доступным пользователю идеям: номер, заголовок, проблема, решение. Запрос ограничен 100 символами. Отсутствие результатов не является ошибкой.

P1-аналитика: количество по категориям и статусам, число идей без ответственного, медиана времени до первого рассмотрения. Пустая выборка отображается как «Нет данных», а не 0% успешности. Ни один график не выдаёт синтетические данные за реальную статистику области.

Не ранжировать жителей или их взгляды. Не использовать популярность, язык, имя или предполагаемый социальный статус как основание отказа. Приоритет реализации — решение сотрудника, не обещание алгоритма.

## 16. FR-12 — публичная витрина, только P1

По умолчанию идеи частные. Для публикации нужны отдельное согласие автора и проверка сотрудника. Публичная карточка создаётся из разрешённой проекции: обезличенное название, очищенное описание, категория, укрупнённая территория, открытый статус. Контакты, исходные файлы, точные адреса и внутренняя история не включаются автоматически.

Похожие идеи для обычного жителя ищутся только среди его собственных и опубликованных обезличенных карточек. Нельзя «утечь» чужую частную идею через рекомендации похожести.

## 18. Определение готовности

MVP готов, когда реальная форма создаёт запись в БД; она видна нужному сотруднику; изменение статуса с комментарием появляется у автора; файл доступен только разрешённым пользователям; сценарий проходит после чистого развёртывания; нет блокирующих ошибок доступа и потери данных.
