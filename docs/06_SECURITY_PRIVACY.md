# 06. Безопасность, данные и границы демонстрации

## 1. Статус документа

Это инженерные требования к прототипу, не юридическое заключение и не подтверждение соответствия всем требованиям промышленной государственной системы. Для хакатона использовать синтетические данные. Для пилота с реальными жителями отдельно согласовать основание обработки, владельца данных, размещение, сроки хранения, обращения пользователей, передачу внешнему AI и процедуру инцидентов.

eOtinish уже существует как официальный канал обращений; наш MVP не следует представлять его официальной заменой или подключённым модулем. Источник S8 в [12_SOURCES_ASSUMPTIONS.md](12_SOURCES_ASSUMPTIONS.md). Прототип не вызывает внешнюю отправку от имени жителя.

## 2. Минимизация

Собирать только имя для отображения, email для входа, текст идеи, территорию и добровольно приложенные материалы. Не требовать ИИН, паспорт, домашний адрес, медицинские документы, дату рождения или сведения о родственниках.

Контакты хранятся в профиле, а не копируются в каждое публичное событие. Свободный текст может всё равно содержать персональные данные — наличие формы согласия не делает такой текст безопасным для автоматической публикации.

Согласие на использование сервиса не объединять с согласием на публичную витрину и внешнюю AI-обработку. Демоистории помечены `is_demo`, адреса вида `citizen@example.test` не являются реальными получателями почты.

## 3. Авторизация и доступ к объектам

Любое чтение/изменение идеи проверяет `actor.regionId`, автора или текущую организацию. Запросы списка сразу ограничиваются scope в SQL, а не фильтруются после получения всех записей. То же касается событий, комментариев, вложений, уведомлений, похожих идей и аналитики.

Для недоступного конкретного объекта возвращать одинаковый `404 NOT_FOUND`. Не раскрывать существование записи разными текстами ошибки. UI не считается границей безопасности.

Права берутся из БД на текущий запрос; изменение роли/организации или деактивация сотрудника не должны оставлять вечные права в старом токене. Администратор ограничен регионом и подчиняется требованиям комментария и статусов.

## 4. Пароли и сессии

Использовать проверенную библиотеку **Argon2id**, исходная конфигурация не слабее 19 MiB памяти, 2 итераций и parallelism 1; параметры фиксировать в хеше. Это ориентир OWASP S9, который B должен проверить вместе с выбранной библиотекой и измерить на стенде. Самодельный SHA-256/MD5 для паролей запрещён.

Если выбранная Argon2-библиотека не собирается в контейнере, B согласует альтернативу, опираясь на S9/S11; не снижает параметры молча. Сравнение секретов выполняется безопасной функцией библиотеки. Ограничить число одновременно выполняемых дорогостоящих password checks.

Сессия: случайный токен не менее 32 байт из криптографического генератора; в БД — его хеш, срок жизни 12 часов, отзыв при выходе. Cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` при HTTPS. На loopback HTTP Secure=false — явное локальное исключение, не публичная конфигурация. После входа токен меняется.

Сессионный и CSRF-токены не хранятся в localStorage, логах, query string и Git. Мутации требуют ожидаемый `Origin` и CSRF-токен, связанный с сессией. Login/register ограничиваются Origin и rate limit, не требуют уже существующей пользовательской сессии.

## 5. Ограничения запросов

Параметризованные SQL-запросы. Разрешённые поля сортировки — whitelist. Ограничить JSON-body 64 KiB; один файл 5 MiB, multipart overhead учесть отдельно; лимиты действуют и на proxy, и на потоковом backend-парсере, а не только на `Content-Length`.

Начальные лимиты демо: 5 неуспешных входов за 15 минут по сочетанию IP+нормализованный email; 20 попыток регистрации в час на IP; 10 отправок идей в час на аккаунт; 30 загрузок файлов в час на аккаунт. Это проектные начальные настройки, которые нужно адаптировать после тестирования, а не универсальные нормативы.

Rate limiting P0 хранится в одной app-инстанции с ограниченной памятью; явно записать ограничение. Для публичного/многосерверного внедрения требуется общий state или внешний gateway. Нельзя доверять произвольному `X-Forwarded-For`; список доверенных proxy конфигурируется.

## 6. Загрузка файлов

Опираться на многослойные меры S10: whitelist форматов, размер, проверка содержимого, безопасные имена, закрытое хранение и контроль доступа. Одного расширения или клиентского MIME недостаточно.

P0 pipeline: поток в ограниченный temp-файл → проверка сигнатуры/типа → для изображения безопасное декодирование с лимитом пикселей → случайный storage key → метадата в БД. Ограничить изображения, например, 20 мегапикселями; проверять переполнение размеров. Оригинальное имя отображается escaped и не участвует в построении пути.

SVG, HTML, JS, исполняемые файлы и архивы не принимаются. PDF не рендерится внутри сайта в P0: только авторизованное скачивание с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`. Валидный PDF всё ещё может быть вредоносным: проверка сигнатуры не заменяет антивирус. Без антивирусного контура демо ограничивается заранее подготовленными синтетическими файлами; до публичного приёма реальных файлов добавить quarantine и сканирование.

`storage_key` не передаётся клиенту. Защита от path traversal: случайные ключи, запрет пользовательских абсолютных путей, проверка корневого каталога. Ошибка загрузки очищает временный файл; периодическая уборка имеет dry-run/лог и не удаляет активные ссылки.

## 7. Контент и браузер

Пользовательский текст выводится как текст. Не использовать `dangerouslySetInnerHTML` для идей, комментариев и AI-ответов. Разрешённый rich text вне MVP. Внешние ссылки не подгружаются сервером автоматически; превью по произвольному URL не реализуется, чтобы не создавать SSRF.

CSP и security headers тестируются вместе с выбранной Next-конфигурацией. Минимум: запрет embedding через `frame-ancestors`, защита от MIME sniffing, ограничение Referrer-Policy. Не обещать строгий CSP, если приложение работает только с отключённой политикой.

## 8. AI и данные

Ключ провайдера — только серверная переменная, не `NEXT_PUBLIC_*`. AI не получает контакты, cookie, пароли, внутренние заметки или файлы автоматически. Redaction текста снижает риск, но не гарантирует отсутствие персональных данных, поэтому внешняя обработка реальных данных отключена до отдельного согласования.

Вход пользователя и документы — недоверенные данные, а не инструкции. AI выдаёт предложения в схеме; application code проверяет enum, каталог и допустимость полей. У модели нет инструмента SQL, смены статуса, shell и рассылки писем. Объяснение модели не используется как доказательство факта внедрения.

## 9. Журналирование и секреты

Логи содержат requestId, route, duration, actorId при необходимости, errorCode. По умолчанию исключить body, email, пароль, токены, полный адрес, оригинальные вложения и сырой prompt. Для разбора AI сохранять минимизированные метаданные и результат, а не скрытые рассуждения.

`.env`, cookies, дампы БД, private uploads, coordination database и credentials не коммитятся. До первого push проверить tracked files и секреты. При утечке секрет отзывается/меняется; простое удаление из последнего коммита не устраняет утечку из истории.

Append-only audit на уровне приложения не является защитой от администратора БД. На защите не называть его блокчейном или неизменяемым доказательством.

## 10. Модель угроз и обязательные проверки

| Угроза | Контроль | Тест |
|---|---|---|
| Житель читает чужую идею | Object-level policy | SEC-01 |
| Чужой орган меняет статус | Organization + region scope | SEC-02 |
| Подмена роли в JSON | Strict DTO + серверная роль | SEC-03 |
| Доступ к файлу по угаданному UUID | Проверка владельца идеи | SEC-04 |
| Скрытая внутренняя заметка в API жителя | Раздельный DTO | SEC-05 |
| Двойная отправка | Idempotency + транзакция | INT-03 |
| Перезапись коллегой | expectedVersion | INT-04 |
| XSS в тексте/AI | Text rendering | SEC-06 |
| CSRF | Origin + session token | SEC-07 |
| Prompt injection | Отсутствие инструментов и schema gate | AI-04 |
| Файл под видом изображения | Проверка MIME/содержимого/лимитов | SEC-08 |
| Демо-вход на обычном production | Feature flag + startup guard | SEC-09 |

## 11. Переход к реальному пилоту

Перед ним нужны назначенный владелец обработки данных; проверенный каталог органов и полномочий; согласованный hosting; юридически проверенные тексты и сроки; процедура удаления/исправления/архива; резервные копии с проверкой восстановления; антивирусный контур; мониторинг; модель инцидентов; подтверждённая идентификация сотрудников; pentest/аудит доступа. Ни один пункт не объявляется выполненным лишь потому, что присутствует в этом ТЗ.
