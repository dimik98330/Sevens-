# 12. Источники, допущения и границы уверенности

**Проверено при подготовке пакета: 29 сентября 2026 года.** Источники ниже подтверждают отдельные технические возможности и ограничения. Продуктовая архитектура, пороги rules-v1, приоритеты P0/P1 и состав команды — проектные решения этого пакета, а не требования процитированных организаций.

## 1. Исходное задание

Источник требований — полный текст слайдов «Хакатон • Smart City • Область Абай / Платформа „Идеи для региона“», вставленный пользователем в беседу. В нём обязательны полный цикл идеи, кабинеты жителя/органа, форма с материалами, фильтрация, ответственный, статусы, REST/БД и роли; AI допускается как дополнительный плюс.

Срок «завтра» и пожелание четырёх агентов с сабагентами — требования пользователя. Официальные часы защиты, состав команды, реальный бюджет, API органов и обязательная интеграция не предоставлены.

## 2. Официальные технические источники

### S1 — Next.js: self-hosting

`https://nextjs.org/docs/app/guides/self-hosting`

Подтверждает self-hosting, внимание к reverse proxy, различие server/public env и особенности кеширования. На этом основании выбран deployable Node-сервер; конкретная конфигурация Docker и модулей — наше решение. Подтверждение документации не заменяет тест конкретной сборки.

### S2 — Docker Compose: порядок запуска

`https://docs.docker.com/compose/how-tos/startup-order/`

Подтверждает зависимости от healthcheck и завершения одноразовой задачи. Используется в требовании `db → init → app`.

### S3 — Drizzle ORM: миграции

`https://orm.drizzle.team/docs/migrations`

Подтверждает поддерживаемые подходы к schema migrations. Выбор единственного владельца миграций и отсутствие production `push` — правило нашей команды.

### S4 — Git worktree

`https://git-scm.com/docs/git-worktree`

Подтверждает несколько рабочих деревьев одного репозитория и их связь с отдельными checkout. Наша схема branch ownership и SQLite-журнал — дополнительные соглашения, не встроенная функция Git.

### S5 — GitHub CLI: создание репозитория

`https://cli.github.com/manual/gh_repo_create`

Подтверждает `gh repo create` и параметры создания из существующего проекта. Доступ к аккаунту, разрешение владельца и реальное выполнение не подтверждены этим источником.

### S6 — Muse Code: продукт и вводная документация

`https://dev.meta.ai/products/muse-code`

`https://dev.meta.ai/docs/overview`

Подтверждают Muse Code как coding-agent и наличие multi-agent возможностей. Конкретные доступы, лимиты аккаунта и установленная у пользователя версия проверяются локально. Не требовать переустановку рабочего WSL-окружения только на основании обновившейся страницы.

### S7 — Muse Code: subagent fanout

`https://dev.meta.ai/docs/cookbook/subagent-fanout`

Документирует `muse --subagent-worktree-isolation`, изолированные дочерние рабочие деревья и управление их жизненным циклом; показанная модель детей имеет глубину 1. Поэтому выбраны четыре независимых основных сеанса, каждый со своим помощником, а не неподтверждённая рекурсивная иерархия. Наличие флага проверяется в установленном CLI.

### S8 — eOtinish

`https://eotinish.kz/ru`

Официальный сайт описывает подачу официальных обращений в госорганы. Наш прототип не заявляется единственным существующим цифровым каналом обращений и не выдаётся за подключённый официальный сервис.

### S9 — OWASP: Password Storage

`https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html`

Источник базового ориентира Argon2id и требования стойкого хранения паролей. Конкретная библиотека, производительность и безопасность интеграции должны проверяться в реализации.

### S10 — OWASP: File Upload

`https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html`

Источник многослойной защиты upload. Проверка расширения и MIME сама по себе недостаточна; реальная готовность требует тестов и дополнительных мер для публичного приёма файлов.

### S11 — Node.js: Crypto

`https://nodejs.org/api/crypto.html`

Официальный reference криптографических primitives, включая случайные данные и password-related APIs. При использовании альтернативы Argon2 сверять API с реально закреплённой версией Node, а не автоматически с latest reference.

### S12 — PostgreSQL 17: locking

`https://www.postgresql.org/docs/17/explicit-locking.html`

Подтверждает механизмы блокировок PostgreSQL. Транзакционный workflow, expectedVersion и обработка гонок в данном проекте — собственные требования и подлежат интеграционным тестам.

## 3. Допущения проекта

| Допущение | Как обозначено / что проверить |
|---|---|
| Русский UI P0 | Согласованный русский текст, казахский ввод; полный KK — P1 |
| Демокаталог территорий | Не полный официальный административный справочник |
| Демоматрица организаций | Не фактический реестр полномочий |
| Регистрация email+password | Не государственная идентификация и не подтверждённый email |
| Файлы на volume | Только persistent Node/Docker deployment; не любой serverless-хостинг |
| 2 постоянных сервиса P0 | app и db; init одноразовый; внешний proxy для публичного HTTPS отдельно |
| AI отключён по умолчанию | Нужны проверенный API-доступ и осознанное включение |
| История append-only в приложении | Не криптографически защищённый неизменяемый журнал |
| Цели latency | Не измеренные результаты |
| Пороги и словарь rules-v1 | Начальные инженерные настройки, не доказанная точность |
| Локальный журнал четырёх агентов | Работает на одном файловом окружении, не облачная оркестрация |

## 4. Что нельзя заявлять на основании этого пакета

«Проект уже разработан»; «четыре агента уже работают»; «GitHub уже создан»; «идея официально отправлена в акимат»; «соответствует всем законам»; «обеспечивает 99% точности»; «впервые в мире»; «успешно выдержал нагрузку» — если соответствующего фактического результата нет.

Пакет задаёт воспроизводимый план реализации и проверки. Готовность приложения устанавливается только результатами coding-команды и тестов на реальном финальном коде.
