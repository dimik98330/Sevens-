# 05. UX/UI: красивый, понятный и реализуемый интерфейс

## 1. Концепция

**«Спокойный цифровой сервис с видимым движением идеи».** Основной интерфейс светлый, читабельный, без перегруженных государственных шаблонов и без неонового dashboard на каждом экране. Один заметный акцент, крупные понятные заголовки, достаточно воздуха, карточки с ясной иерархией.

Название: «Идеи для региона». Подпись: «Цифровые решения для области Абай». Главный текст: **«Предложите идею. Следите за её развитием.»** Подзаголовок: «Опишите проблему и цифровое решение — платформа поможет определить направление и сохранить диалог со специалистом».

Не использовать государственные гербы и официальные знаки так, чтобы прототип выглядел действующим государственным сервисом. Демо-баннер всегда доступен, не спрятан в футере.

## 2. Визуальная система

| Токен | Значение |
|---|---|
| Основной фон | `#F5F7FB` |
| Поверхность карточки | `#FFFFFF` |
| Основной текст | `#14243B` |
| Вторичный текст | `#536174` |
| Акцент / основная кнопка | `#176B5B` |
| Граница | `#DCE3EA` |
| Информационный фон | `#EAF2FF` |
| Радиус карточки / поля | 16 px / 10 px |
| Базовый шаг отступов | 4 px; основные промежутки 8, 12, 16, 24, 32 |
| Основной текст | 16 px, line-height 1.5–1.6 |
| Заголовок страницы | 28–36 px desktop; 24–28 px mobile |
| Минимальная зона нажатия | 44 × 44 px |
| Максимальная ширина контента | 1200 px; формы 760 px |

Контраст проверяется на реально применённых сочетаниях, а не считается гарантированным только из таблицы. Статусы различаются цветом, текстом и пиктограммой. Не использовать один красный/зелёный кружок как единственный носитель смысла.

Шрифт — системный sans-serif стек с полноценной кириллицей и казахскими символами. Подключение внешнего CDN-шрифта не обязательно. Декоративные иллюстрации и библиотеки анимаций не должны блокировать первый экран.

## 3. Информационная архитектура

```text
Главная
  ├─ Как работает
  ├─ Предложить идею → вход → мастер подачи
  └─ Войти
Житель
  ├─ Мои идеи
  ├─ Черновики
  ├─ Карточка идеи
  └─ Уведомления
Сотрудник
  ├─ Очередь предложений
  ├─ Карточка и обработка
  └─ Уведомления
Администратор
  └─ Ручной разбор / исправление маршрута
```

Не создавать отдельную страницу ради каждой вкладки, когда можно использовать одну понятную карточку. Не открывать главное действие в длинной цепочке модальных окон.

## 4. Экран 1 — главная

Верхняя панель: логотип-текст, «Как работает», переключатель языка при готовом переводе, «Войти». Первый экран: заголовок, краткое пояснение, кнопка «Предложить идею», вторичная «Как проходит рассмотрение».

Справа или ниже на мобильном — **пример карточки идеи**, а не случайная фотография здания. Показать «Умные светофоры рядом со школой», категорию и небольшую линию «Идея → Направление → Ответ». Обязательно подпись «Пример».

Ниже — три коротких шага: опишите идею; получите понятный маршрут; следите за ответом. Затем направления в компактной сетке. Не выводить выдуманные «15 000 жителей», «98% решений», «250 внедрённых проектов».

## 5. Экран 2 — вход

Поля email и пароль, кнопка «Войти», ссылка регистрации. Ошибки без уточнения существования email. Пароль можно показать/скрыть кнопкой с доступным названием.

Демонстрационные профили показывать только при разрешённом деморежиме. Кнопки не должны менять роль в браузере или записывать роль в localStorage. Если реализованы быстрые профили, они создают ограниченную серверную демосессию и недоступны на обычном публичном запуске. Более простой P0 — обычный вход с выданными seed-учётными данными.

Для защиты удобнее два отдельных browser profile: житель и сотрудник. Две вкладки одного профиля разделяют cookie и не являются двумя независимыми пользователями.

## 6. Экран 3 — «Мои идеи»

Заголовок, кнопка «Новая идея», компактный фильтр статуса, список. Карточка: название, номер, статус, территория, дата последней активности. Запрос уточнений выделяется фразой **«Нужен ваш ответ»**, а не только цветом.

Пустое состояние: «Пока нет идей. Начните с проблемы, которую замечаете каждый день». Кнопка «Предложить первую идею».

Загрузка — skeleton карточек. Ошибка — короткое сообщение с повтором, а не бесконечный spinner. Черновик содержит действие «Продолжить», отправленная идея — «Открыть».

## 7. Экран 4 — мастер подачи

### Шаг 1. Что предлагаете

Поля: название; проблема; решение. Подсказки объясняют разницу: «Что сейчас неудобно?» и «Как цифровая технология может помочь?». Ожидаемая польза необязательна.

Пример названия не должен автоматически становиться пользовательским вводом. Счётчик символов появляется ближе к лимиту. Нажатие «Далее» показывает конкретные ошибки, переводит фокус к первой из них.

### Шаг 2. Где и в каком направлении

Выбор территории; уточнение места; категория с вариантом «Определить автоматически»; загрузка материалов. Зона файла поддерживает и drag-and-drop, и обычную кнопку выбора. Рядом: «До 3 файлов, JPG/PNG/WebP/PDF, каждый до 5 MiB». Статусы загрузки отдельные для каждого файла, есть понятное сообщение об отказе.

Поле географии — справочник, а не обязательная интерактивная карта. Карта может быть P1 и не должна зависеть от платного ключа или интернет-тайлов в основном demo-flow.

### Шаг 3. Проверка

Показать паспорт: название, проблема, решение, территория, категория, материалы. Согласие отдельным checkbox. В кнопке «Отправить идею» нет скрытого согласия на публичную публикацию.

Во время запроса кнопка блокируется и меняет текст на «Отправляем…». После сетевой ошибки пользователь может повторить то же намерение с тем же Idempotency-Key. Не показывать конфетти до подтверждения сервера.

Успех — номер идеи, текущая очередь, объяснение маршрута, кнопка «Открыть идею». TRIAGE объяснять нормально: **«Несколько направлений. Специалист уточнит маршрут»**, а не «AI не справился».

## 8. Экран 5 — карточка жителя

Верх: номер, название, статус. Далее компактный блок **«Сейчас происходит»**: текущая организация, последнее публичное действие, следующий доступный шаг. После него — исходная идея и материалы.

История — вертикальная лента, а не процентный progress bar. Статусы `NEEDS_INFO` и `REJECTED` не являются линейными процентами реализации. В событии видны дата, действие, публичный комментарий.

При `NEEDS_INFO` форма ответа находится сразу под вопросом сотрудника. Подпись «Ваш ответ добавится в историю, исходный текст идеи сохранится». После успешного ответа блок заменяется подтверждением и новым статусом.

При `COMPLETED` показывать тип результата: «Предоставлен итоговый ответ» не заменять автоматически на «Проект реализован».

## 9. Экран 6 — очередь сотрудника

Левая навигация desktop: «Предложения», «Без ответственного», «Нужны уточнения»; аналитика только при реализации. Сверху имя демонстрационной организации и поиск.

В таблице не более 7–8 основных колонок; длинный текст обрезается визуально, полное название доступно при открытии. Фильтры размещаются в одной панели с кнопкой «Сбросить». Сортировка и текущая страница сохраняются при возврате из карточки.

Мобильный экран использует карточки вместо горизонтальной таблицы. Для фильтров — выдвижная панель с теми же доступными полями.

Пустое состояние фильтра: «По выбранным условиям идей нет» + «Сбросить фильтры». Это отличается от общей пустой очереди.

## 10. Экран 7 — обработка идеи

Основная колонка — содержание, файлы, публичный диалог. Правая — маршрут, ответственный, статус, действия. На мобильном блок действий переносится под заголовок; важные кнопки не перекрывают форму и клавиатуру.

Визуально разделить **«Ответ жителю»** и **«Внутренняя заметка»**. Переключатель видимости имеет явную подпись, а внутренний блок — заметное предупреждение. Перед отклонением или завершением показывать текст, который увидит автор, и требовать подтверждение действия.

При конфликте версии: «Коллега уже изменил эту идею. Обновите карточку перед сохранением. Ваш текст сохранён в форме». Не терять комментарий и не выполнять действие повторно автоматически.

## 11. Экран 8 — объяснение маршрута

Это узнаваемый элемент продукта. Карточка «Почему это направление?» содержит основную тему, дополнительные теги, найденные признаки и текущую демонстрационную организацию.

Для жителя достаточно 2–3 предложений. Служебный вид может раскрывать версию правил и основание ручной коррекции. Исходный выбор автора и рекомендация показываются раздельно. При AI P1 рядом всегда указан источник: «Правила», «AI-рекомендация», «Исправлено сотрудником».

Не показывать технический JSON, токены и цепочку внутренних размышлений LLM обычному жителю.

## 12. Тексты состояний

| Ситуация | Текст |
|---|---|
| Сбой AI | «Дополнительный анализ недоступен. Идея сохранена, маршрут определён базовыми правилами» |
| Неопределённый маршрут | «Идея передана в демонстрационный центр разбора направлений» |
| Сбой сохранения черновика | «Не удалось сохранить изменения. Поля остаются открытыми — попробуйте ещё раз» |
| Отказ в доступе | «Страница недоступна или у вас нет доступа к этой идее» |
| Ошибка файла | «Этот формат не поддерживается. Выберите JPG, PNG, WebP или PDF» |
| Демо-баннер | «Прототип хакатона. Реальная отправка в государственные системы не выполняется» |
| Не готовая возможность | «Не входит в текущую демонстрацию»; лучше убрать неработающую кнопку |

## 13. Языки и доступность

P0 — полностью согласованный русский интерфейс и вынесенные текстовые ключи. Казахский контент пользователя хранится и отображается корректно. P1 — полный перевод UI на казахский с ручной проверкой носителем/командой; не выдавать машинный перевод за проверенный.

Нельзя показывать переключатель KK, который оставляет половину интерфейса на русском без предупреждения. При отсутствии полного перевода переключатель скрывается, а готовность локализации отмечается в отчёте.

Поля имеют label, помощь и ошибки связаны через `aria-describedby`; модальные окна удерживают/возвращают фокус; loading не меняет layout резко. Уведомления об успехе доступны через `aria-live`. Учитывать `prefers-reduced-motion`.

## 14. Визуальная приёмка

Обязательные screenshots: главная; пустой список; заполненная форма; ошибки; карточка с историей; очередь сотрудника; изменение статуса; конфликт версии. Размеры: 390×844 и 1366×768; дополнительно ручной контроль 360 px.

D проверяет не «красиво вообще», а отступы, читаемость, отсутствие обрезанного текста, работающие состояния, контраст, клавиатуру и соответствие этому документу. Перерисовка визуальной системы перед самой защитой запрещена, если основной сценарий уже стабилен.
